# Azure OpenAI is the second provider, reached through a managed identity, on a Data Zone EU deployment with key auth disabled

**Status: draft.** Written before the live proof (ticket 19) so the decision and the questions the proof must settle are recorded first. Lines marked "to be settled by the live proof" are open; nothing here reports a result that does not yet exist. The provider comparison is ticket 20 and its verdict is ADR-0015; this ADR is amended only with the live-proof results.

The brief (§10) asks for Azure OpenAI as a second provider that Container Apps reaches through a managed identity, "so there is no key for that path", and for an eval report comparing the providers. ADR-0013 left the Anthropic path without an EU-only processing guarantee. This ADR records how the Azure path is built and what holds its credential, which is nothing.

**Decision.**

1. **A Data Zone Standard (EU) deployment.** One Azure AI Services account in `northeurope` holds a `gpt-5.4` deployment (model version 2026-03-05, SKU `DataZoneStandard`, priced at $2.75 / $16.50 per million tokens, ticket 01). Processing stays inside the EU Data Zone, which the Anthropic path cannot claim.
2. **Key authentication is disabled on the account** (`disableLocalAuth`). There is no API key to leak, rotate or store, in GitHub, in Container Apps or in `.env.azure`. The account has a custom subdomain, which Entra token authentication requires.
3. **The container app has a system-assigned managed identity** with the role `Cognitive Services OpenAI User` on the account alone: it can call the model and can do nothing else to the account.
4. **No key path exists in code.** `label.azure_openai` builds `AzureChatOpenAI` with a token provider from `DefaultAzureCredential` (the environment credential excluded, so a stray `AZURE_*` variable cannot change who the app is), passes the key arguments as explicit `None`, and refuses a key, a token, a base URL or headers in `CVR_LABEL_EXTRA` as `LabellerMisconfigured`. A test pins this. In Container Apps the default credential resolves to the managed identity; on a developer machine it resolves to `az login`.
5. **The switch is configuration, not code or image.** `scripts/switch-provider.sh azure` sets `CVR_LABEL_PROVIDER`, `CVR_LABEL_MODEL`, `CVR_LABEL_EFFORT`, `CVR_LABEL_AZURE_ENDPOINT` and `CVR_LABEL_AZURE_DEPLOYMENT` on the app; `anthropic` removes them, which returns the app to the deployed default (ADR-0011). The same image serves both. The proof runs the switch, `demo.sh up`, the smoke test, `demo.sh down`, the switch back and `demo.sh down` again, and ends on an empty replica list, because each update makes a revision that may start a replica (ADR-0010 amendment).

**The eval's identity, a decision applied only if Azure wins (ticket 21).** The CI eval would need to call the same account to compare the providers on the gate. It would do so as a second, narrow identity reached through the same OIDC federation as the deploy (ADR-0010): a separate Entra app registration, federated to the `eval` job's subject, holding `Cognitive Services OpenAI User` on the account and nothing on the resource group. The existing deploy identity is not widened, and no key is created. If Anthropic stays the default, the comparison is run once by the maintainer from a signed-in shell and this identity is never created.

**To be settled by the live proof (ticket 19).**

- **Token scope.** `https://ai.azure.com/.default` (the code's default, from Microsoft's managed-identity guide, ticket 01) against `https://cognitiveservices.azure.com/.default` (the older scope). Result: _to be settled by the live proof_. The proof can try the second without a code change: `CVR_LABEL_AZURE_SCOPE=... sh scripts/switch-provider.sh azure`.
- **API version.** `2025-04-01-preview` (the code's default). Result: _to be settled by the live proof_; `CVR_LABEL_AZURE_API_VERSION` overrides it the same way.
- **Nesting limit.** Azure's strict structured outputs allow five levels of nesting. `Labelling` is four levels by objects and six if arrays count. Whether the service counts arrays: _to be settled by the live proof_. If it does and rejects the schema, the fix is a schema bump (ADR-0009) and an eval on the deployed provider, not a workaround in the proof.
- **Whether the identity's role assignment has propagated** in time for the first call (a 401 or 403 in the first minutes may be propagation, not configuration): _to be settled by the live proof_.

**Considered options:** An API key in a Container Apps secret (rejected: it is exactly the credential the brief wants absent, and it would be a second secret to rotate beside the API key). A user-assigned identity (rejected for now: one app, one account, and the system-assigned identity dies with the app, so there is nothing to clean up; a user-assigned identity is what a second app would justify). Reusing the deploy's Entra app for the eval (rejected: it holds Contributor on the resource group, far more than a model call needs). Setting the switch in the provisioning wizard (rejected: the wizard runs once, the switch is repeated and reversible, and the app is off by default).

**Consequence:** the Azure path has no secret anywhere, and the proof is repeatable by script. The price is that the first live call is the first time the scope, the API version and the schema meet the real service; the offline strict-schema test (`tests/label/test_azure_strict_schema.py`) cannot settle the nesting question. The app must be left off after the proof, as ADR-0010 requires, and a proof that ends with a running replica is not finished.
