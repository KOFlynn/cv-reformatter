# Azure OpenAI is the second provider, reached through a managed identity, on a Data Zone EU deployment with key auth disabled

**Status: accepted, 2026-10-29.** Written before the live proof (ticket 19) and amended with its results, which are in the section below. The provider comparison is ticket 20 and its verdict is ADR-0015.

The brief (§10) asks for Azure OpenAI as a second provider that Container Apps reaches through a managed identity, "so there is no key for that path", and for an eval report comparing the providers. ADR-0013 left the Anthropic path without an EU-only processing guarantee. This ADR records how the Azure path is built and what holds its credential, which is nothing.

**Decision.**

1. **A Data Zone Standard (EU) deployment, in swedencentral.** One Azure AI Services account in `swedencentral` holds a `gpt-5.4-mini` deployment (model version 2026-03-17, SKU `DataZoneStandard`, priced at $0.825 / $4.95 per million tokens, Azure Retail Prices API, checked 2026-10-24). Processing stays inside the EU Data Zone, which the Anthropic path cannot claim. The account's region differs from the Container App's (`northeurope`) on purpose: a Data Zone deployment is billed and processed by zone, not by the caller's region, and the region of the account only decides which regional quota applies. The first plan was a `gpt-5.4` deployment (2026-03-05, $2.75 / $16.50) in `northeurope`; on 2026-10-24 the maintainer's live run of the wizard found that `cvr_sub` has 0 interactive quota for gpt-5.4 everywhere (northeurope Global and Data Zone rows all 0.0), and a read-only check across EU regions found the only EU Data Zone Standard chat model with quota is gpt-5.4-mini, 200 (thousand TPM) in swedencentral, westeurope, germanywestcentral and francecentral, not northeurope. So the account is in swedencentral and the provider comparison (ticket 20) is gpt-5.4-mini against Sonnet 5.5. A Data Zone Standard quota request for gpt-5.6-terra (version 2026-07-09, swedencentral) was refused 2026-10-29 (Sweden Central has no capacity to expand; Microsoft: resubmit with other regions or wait 30+ days). The comparison is therefore gpt-5.4-mini against Sonnet 5.5. The wizard still accepts `gpt-5.6-terra` and `gpt-5.4`, and both are priced, in case quota appears later: re-running with `AZURE_OPENAI_MODEL=<model>` would add that deployment to the same account and leave gpt-5.4-mini alone (deployments are named after their models). Cross-region calls between the app and the account are over the public endpoint with token authentication, as they would be in one region; the cost is some extra network latency, which the comparison's wall time will show.
2. **Key authentication is disabled on the account** (`disableLocalAuth`). There is no API key to leak, rotate or store, in GitHub, in Container Apps or in `.env.azure`. The account has a custom subdomain, which Entra token authentication requires.
3. **The container app has a system-assigned managed identity** with the role `Cognitive Services OpenAI User` on the account alone: it can call the model and can do nothing else to the account.
4. **No key path exists in code.** `label.azure_openai` builds `AzureChatOpenAI` with a token provider from `DefaultAzureCredential` (the environment credential excluded, so a stray `AZURE_*` variable cannot change who the app is), passes the key arguments as explicit `None`, and refuses a key, a token, a base URL or headers in `CVR_LABEL_EXTRA` as `LabellerMisconfigured`. A test pins this. In Container Apps the default credential resolves to the managed identity; on a developer machine it resolves to `az login`.
5. **The switch is configuration, not code or image.** `scripts/switch-provider.sh azure` sets `CVR_LABEL_PROVIDER`, `CVR_LABEL_MODEL`, `CVR_LABEL_EFFORT`, `CVR_LABEL_AZURE_ENDPOINT` and `CVR_LABEL_AZURE_DEPLOYMENT` on the app; `anthropic` removes them, which returns the app to the deployed default (ADR-0011). The same image serves both. The proof runs the switch, `demo.sh up`, the smoke test, `demo.sh down`, the switch back and `demo.sh down` again, and ends on an empty replica list, because each update makes a revision that may start a replica (ADR-0010 amendment).

**The eval's identity, a decision applied only if Azure wins (ticket 21).** The CI eval would need to call the same account to compare the providers on the gate. It would do so as a second, narrow identity reached through the same OIDC federation as the deploy (ADR-0010): a separate Entra app registration, federated to the `eval` job's subject, holding `Cognitive Services OpenAI User` on the account and nothing on the resource group. The existing deploy identity is not widened, and no key is created. If Anthropic stays the default, the comparison is run once by the maintainer from a signed-in shell and this identity is never created.

**Settled by the live proof (ticket 19, 2026-10-29).** Locally first (the maintainer's `az login`, through the Azure CLI credential in the default chain) and then in Container Apps through the managed identity, both on the `gpt-5.4-mini` deployment.
- **Token scope: `https://ai.azure.com/.default`**, the code's default, worked from the managed identity; the `cognitiveservices` fallback was not needed. The app answered a real `/reformat` with HTTP 200 (run id `db24fcfa61dd454c93d9b45b72fe8cee`; the app's log shows provider `azure_openai`, model and deployment `gpt-5.4-mini`, effort `medium`, 3110 input and 2848 output tokens, no failure, no retry).
- **API version: `2025-04-01-preview`**, the code's default, was accepted with `reasoning_effort`, `max_completion_tokens` and strict structured outputs.
- **Nesting limit: not an issue for this schema.** The strict `Labelling` schema was accepted by the service on the first call (locally and in the app), so no schema bump was needed. This does not say how Azure counts arrays in general; only that `Labelling` as it stands passes.
- **Role propagation was not an issue**: the grants had been made minutes before and the first call succeeded. A 401 or 403 in the first minutes should still be read as possible propagation before it is read as misconfiguration.

**Considered options:** A northeurope account (rejected: no quota there for any EU Data Zone chat model on this subscription, 2026-10-24; moving the Container App to match was rejected as churn for a quota issue, and the app has nothing to do with the account's region). An API key in a Container Apps secret (rejected: it is exactly the credential the brief wants absent, and it would be a second secret to rotate beside the API key). A user-assigned identity (rejected for now: one app, one account, and the system-assigned identity dies with the app, so there is nothing to clean up; a user-assigned identity is what a second app would justify). Reusing the deploy's Entra app for the eval (rejected: it holds Contributor on the resource group, far more than a model call needs). Setting the switch in the provisioning wizard (rejected: the wizard runs once, the switch is repeated and reversible, and the app is off by default).

**Consequence:** the Azure path has no secret anywhere, and the proof is repeatable by script (`switch-provider.sh`, then `demo.sh up`, the smoke test and `demo.sh down`, ADR-0010). The first live call met the scope, the API version and the schema together and all three worked as the code had them. A model-quality result from the local check (the gate failed one document on quality: `RM_REFEREE` removed a content line) is for the comparison, ticket 20, not a setup fault. The app is left off after the proof, as ADR-0010 requires: the revision was deactivated and the replica list printed 0.
