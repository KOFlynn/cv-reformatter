# The labeller reaches Claude through LangChain's native structured output, never a forced tool call, and returns a value, never raises

ADR-0001 already draws the line: the LLM labels, code transforms. This ADR is about how the label step itself is built once it has to actually reach a provider, because "reach a provider" has three different-looking failure modes that all have to collapse into the same shape as a normal answer: a bad network day, a response that doesn't parse as JSON, and a response that parses but doesn't match the schema. All three become a `LabellingFailure` value returned from the same function that returns a `Labelling` on a good day; nothing in `cvr.label` ever raises out to the pipeline. The consequence downstream is already decided by ADR-0008: a labelling failure is a request-level outcome, every block becomes residue, and the document is banner and appendix. A retry loop belongs to Phase 2's LangGraph, not here.

**LangChain, for the provider swap Phase 2 needs, not for orchestration.** The label node is a plain function today; LangChain buys one thing now, the chat-model interface, so that Azure OpenAI in Phase 2 is a different `init_chat_model` call against the same schema and the same verifier, not a rewrite. `init_chat_model(model=config.model, model_provider=config.provider, **anthropic_kwargs(config))` is the whole construction; `anthropic_kwargs` is the one function in `cvr.label` that knows an Anthropic field name (`reasoning_effort`, and `temperature` only when `LabellerConfig.temperature` is set), so a second provider's configuration function is a sibling, not a rewrite of this one. `LabellerConfig` — provider, model, effort, optional temperature, any other sampling knob — is read from the environment (`CVR_LABEL_*`) once and threaded through every report; a change to any field is a model change under the eval-run rule, so it has to be visible, not buried in a constructor call.

**Structured output through Claude's native `json_schema` method, not a forced tool call.** `with_structured_output(Labelling, method="json_schema")` asks Claude's own structured-output feature to fill the schema; the alternative, `method="function_calling"`, forces a tool call, and a forced tool call is incompatible with the adaptive thinking the effort setting turns on — LangChain's own Anthropic integration falls back to an unforced call under thinking anyway, which reintroduces the failure mode native structured output was meant to remove. `include_raw=True` is set unconditionally so a parsing failure comes back as data (`{"raw": ..., "parsed": None, "parsing_error": ...}`) instead of an exception, and so the raw message's `usage_metadata` is available whether or not parsing succeeded — a labelling failure still has an accurate token count and cost.

**The schema sent is ticket 03's `Labelling` type, unmodified.** `Labelling.model_json_schema()` is what is sent; there is no second schema hand-built for the wire, because a second schema is a second place the two can drift. It is strict-compatible from day one — every property required, no `additionalProperties`, `null` in place of optional, asserted by `tests/models/test_labelling.py` — because that is also Azure OpenAI's strict-mode shape in Phase 2, and building it twice would mean testing it twice. The removals list's `rule` is `TextRemovalRule`, the closed `Literal` of the eight text rules; the ninth, `RM_PHOTO`, is not in it and never will be, because the parser removes every image deterministically at parse and the LLM never sees one. **If code can do it deterministically, the LLM doesn't get a vote** — the same reasoning ADR-0008 applies to the heading backstop applies here to photos, just earlier in the pipeline.

**The prompt is a file, not a string in the code, and it is versioned as data.** `prompt.md` sits inside `cvr.label`, loaded once at import; `PROMPT_VERSION` and `SCHEMA_VERSION` are hand-bumped strings, and `CONTENT_HASH` is a hash of the prompt text plus the JSON schema, computed once at import and never recomputed from a cache. The version labels are for a human reading a report ("prompt 1.1.0"); the hash is for catching the human being wrong — a bumped label with no text change, or a text change with no bump, is a hash mismatch nothing else would show. All three ride on every `LabelRun` (and, once ticket 06 lands, every pipeline `Run`), never just in a log line that can scroll away.

**What it costs and what bounds it.** Quotes copy the CV, so output tokens dominate the bill; `PRICE_TABLE` in `cvr.label.pricing` is one dict, USD per million tokens, with the date it was checked against `claude.com/pricing` recorded beside it — checked 2026-09-23: Opus 5 at $5/$25, Sonnet 5 at $2/$10 per million input/output tokens. `estimate_cost` reads it per request; an unrecognised model costs zero rather than raising, because a labelling failure must never crash on the way to reporting itself. The spec's own baseline — roughly $7 per 48-document run on Opus 5, $3 on Sonnet 5 — is what the response cache and CI concurrency cancellation (Phase 1, later tickets) are built to bound; this ADR only supplies the number the cache key and the report multiply by.

**The eval is the labeller's test, deliberately.** One spike test reaches the real model, skipped without `ANTHROPIC_API_KEY`, and proves the wiring — native structured output, adaptive thinking and effort together — reaches the provider and comes back schema-valid on the default model. It is not where prompt quality is judged; the golden set and the nine metrics are. Everything else in `cvr.label` — the config, the version and hash bookkeeping, the pricing, and turning a canned response into a result or a failure — is unit-tested against a fake structured-output `Runnable` standing in for a bound chat model's `include_raw=True` output, because LangChain's built-in fake chat models do not implement `with_structured_output`. No test in this suite, or anywhere else in the repository, calls a real model; CI never needs a key to pass.

**Why no endpoint will ever expose the transform log.** The `Run` (and the `LabelRun` this ticket produces as its precursor) holds exactly the material a reviewer would want to second-guess a placement or a removal: the ledger, the rejections, the residue, the prompt that produced them. Publishing that as a queryable resource is the first half of a review queue — a second product this project does not build. The transform log is printed to standard output for the operator running the pipeline and read in-process by the eval runner; `GET /health` and `POST /reformat` never return it, and no ticket after this one should add a route that does.

**Considered options:** forced tool calling for structured output (rejected: incompatible with adaptive thinking, the same failure mode `method="json_schema"` exists to avoid). Hand-building a second, wire-specific JSON schema (rejected: `Labelling.model_json_schema()` is already strict-compatible; a second schema is a second thing to keep in sync). Letting the labeller retry internally on a bad response (rejected: retries are Phase 2's LangGraph, and a Phase 1 retry loop would hide the request-level failure this ADR is about surfacing cleanly). Raising on a malformed or schema-invalid answer (rejected: ADR-0008's whole point is that a bad day for the LLM is a document under the banner, never an error page). A prompt constant inside `labeller.py` instead of a file (rejected: a file is what gets a version label and a diff).

**Consequence:** `cvr.label` is the one package in the pipeline that reaches the network, and it is exercised by exactly two kinds of test: fast ones that never leave the process, and one spike that is opt-in by the presence of a key. The pipeline (ticket 06) receives a plain `blocks -> labelling result` callable and, per call, a `LabelRun` to fold into its own `Run`; a second provider is a second `init_chat_model` call and a second provider-configuration function, not a rewrite of the schema, the prompt loading, the version bookkeeping, or the failure handling.
