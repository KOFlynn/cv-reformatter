# The pipeline is a LangGraph graph whose one loop is a bounded, additions-only retry

Phase 1 ran the five nodes as a straight function. When the labeller misquoted or missed text, that text went to the review appendix and nothing asked the model to try again, though the brief's architecture has always drawn a retry loop. Phase 2 puts the nodes on LangGraph and adds the loop, under the invariant of ADR-0001: the model labels, it never writes output text.

**Decision.** `reformat` builds a `StateGraph` of the same five nodes (`parse`, `label`, `verify`, `transform`, `render`) with one conditional edge, from `verify` back to `label`. The edge is taken while the retry rules say so, and only while **unplaced text** remains and attempts are left. Everything else is a line. The graph is built per call, with no checkpointer and no streaming; the labeller stays injected, so no node but `label` reaches a model.

**What a retry is.** A retry sends the model every block, its first answer and **feedback**: the unplaced runs (block id and offsets) and, as hints, the `unlocatable` rejections in those blocks. It answers with `Additions` only: `{path, reference}` pairs addressed into the first answer's tree. `verify` then runs over the first answer followed by the additions, in one pass, so the ledger of ADR-0008 decides every conflict.

- **Additions only, and the first answer always wins.** Additions are placed after the whole first-answer walk. A retry can fill an empty leaf, append to a list or open a new entry; it cannot remove, replace or move anything placed, so a retry can only improve a document. `conflict` and `removed` rejections are never feedback, since an additions-only retry cannot change them.
- **The path grammar** (ticket 11): `name`; a list `profile|skills|certifications|additional`; `experience[i].title|employer|location|dates|bullets`; `education[i].institution|qualification|dates|details`. A list path appends and a leaf path fills an empty leaf. `i` equal to the current entry count opens a new entry; above it, or a non-canonical number, is the rejection `bad_path`. "Empty" means empty after verification: a leaf the first answer referenced but verify rejected is still addressable, since otherwise the retry could never repair the leaves its hints are about. A new entry that ends with nothing placed is dropped.
- **Additions accumulate.** Retry *k* verifies the first answer plus the additions of every successful retry so far, in order.
- **Hints come only from the base answer.** The paths of an addition's own rejection address the additions, which the labeller cannot look up, so only the base answer's `unlocatable` rejections are hints. The unplaced runs are always sent whole.
- **A failed first attempt is re-asked with the first prompt.** An `Additions` answer cannot carry removals, so retrying "to an empty tree" would leave referees and addresses unremoved and in the appendix. The re-ask calls the labeller as the first attempt did; a usable `Labelling` becomes the base answer and later retries add to it. It is still a retry: it counts against N, and `Run.label` stays the failed first attempt.
- **N** is `CVR_RETRY_MAX`, default 2, read once per Run by `retry_max()` (non-numeric or negative fails at start-up naming the variable; 0 turns the loop off). A retry is allowed while `attempts <= N`, so N = 2 allows attempts 2 and 3.
- **The loop stops** on nothing unplaced, attempts exhausted, a retry that did not reduce the unplaced non-separator characters (**no progress**; whitespace and separators count for nothing, so a document whose only residue is a separator never retries), a retry that was a labelling failure or a provider outage (the previous verified result is kept, so a usable document is never turned into a 503). (A provider outage on the first attempt keeps its Phase 1 meaning: the request fails.)
- **A labeller that cannot take feedback makes one attempt.** The oracles are untouched.

**The Run records it.** `Run.retries` (omitted from the JSON when empty) holds one `RetryRun` per retry: the attempt's `LabelRun`, the feedback as ids, offsets and paths (no text), the rejections it produced and the unplaced characters left after it. `Run.label` stays the first attempt, and `Run.label_runs` lists the first attempt then each retry that has a record, which is what cost and token totals sum over (the API's summary line and the eval report). The trace has a span per node visit, a generation per attempt and a `retry_decision` event under each `verify` visit; no mode puts text in the decision.

**In the eval.** The response cache stores each attempt on its own. The first attempt's key is the Phase 1 key (configuration, prompt and schema hashes, source sha256). A later attempt's key hashes that key with the attempt number, the retry prompt and additions schema hashes, and the hashes of the feedback and of the base answer it was sent. The blocks, the configuration, the four content hashes, the base answer and the feedback are everything a retry's answer depends on, so a cached run replays the same retries with no call; the attempt number keeps the re-ask of a failed first answer from replaying the failure it follows. The report gains three columns, per layout, tag and candidate and in the totals: **retries fired**; **characters placed by a retry**, the unplaced non-separator characters the retries took out of the appendix (the count before the first retry, read from its feedback's runs, minus the count after the last, clamped per retry at zero, with a re-ask of a failed first answer counting nothing itself); and **retry cost**. Tokens and cost sum every attempt. The thresholds are unchanged, deliberately: the retry is judged against the bar Phase 1 set.

**The pattern the eval should show.** Candidates c09 and c11 carry deliberate unplaceable fragments in every Layout, so each of those eight documents fires exactly one retry, which makes no progress and ends the loop, and the fragment goes to the appendix as before. A document whose first attempt placed everything fires none. A retry anywhere else, or two on one document, is a deviation to explain; a rise in retries on the fully placed documents is cost creep. The live run for this ADR is the pull request's CI eval report.

**Considered options.**

- *Retry by re-labelling the whole document* (rejected): a second full answer can move or drop what the first placed, and the verifier would have to merge two trees. Additions make "a retry can only improve the document" true by construction.
- *Retry on `conflict` or `removed` rejections* (rejected): additions cannot change them, so the call would be wasted.
- *A graph with a checkpointer or streaming* (not now): a request is one short run; neither earns its dependencies.
- *Passing N through the labeller or `reformat`'s signature* (rejected): N is pipeline policy, so `label` must not hold it, and the spec adds only the tracer to `reformat`.

**What would change.**

- **Neighbouring-block feedback.** Feedback sends every block's text to the model on each retry. Trimming it to the blocks around the unplaced runs would cut tokens, at the risk of addressing paths into entries the model can no longer see.
- **Leaner feedback.** Fewer hints, or none, may place just as much. This is measurable on a failure-prone model such as Haiku, where the first attempt leaves real residue, and would then be confirmed on the deployed model; on Sonnet the eval has only the c09/c11 fragments to learn from.
- A retry on `conflict` or `removed`, or one that may replace an earlier answer, would need the first answer no longer to win every conflict: a different invariant, a different ADR.

**Consequence.** Uncached, each eval adds about eight retry calls to the roughly $1.60 of the first attempts, and the report now says exactly how many, what they placed and what they cost. Changing the retry prompt, the additions schema or the feedback moves only the retries' keys, so the first attempts' cached answers survive it; changing the first prompt or schema moves every key.
