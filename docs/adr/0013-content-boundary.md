# The content boundary: the LLM provider sees the CV, no other third party does, and our logs keep text but never PII

Phase 2 adds tracing in Langfuse. Before it, the deployed app already wrote every word of every CV to Log Analytics, PII values included, and a labelling failure's reason repeated the model's own text because it was built from the pydantic error. Sending text to a third-party tracing service on top of that would have made the exposure worse unless the boundary was designed rather than assumed. This ADR says where candidate text may go, what holds it there, and the test that shows it. The documents are synthetic, so nothing here is a breach; it is the shape a real deployment would need, and the evidence that the shape holds.

**Decision.** There are four places candidate text can be, and each has a rule.

1. **The LLM provider receives the CV text on every run.** That is what labelling is: the blocks go out in the prompt and the references come back. Today the provider is Anthropic (Sonnet 5.5 at `medium`, ADR-0011). The Anthropic path has no EU-only processing guarantee; for real CVs that would weigh against it.
2. **Beyond the provider, candidate text reaches no third party.** Langfuse (Cloud, EU region, Hobby plan, a private project) receives **structure only** in production: ids, counts, closed-vocabulary reasons, timings, tokens and cost. The one exception is the CI eval, which sets `CVR_TRACE_MODE=full` and so also sends the blocks, the rendered prompt, the raw answer and the rejections' quotes; its documents are the generated golden set, which is synthetic. The deployed app never sets the mode (a static test over the workflow, the scripts and the Dockerfile pins that), and the API logs a warning at startup if it ever finds it set.
3. **The logs keep text inside our tenant, minus PII.** The transform log goes to standard output and so to Log Analytics in our own subscription. It holds the text a reviewer needs (headings removed, dates, unplaced residue) and, for every removal under a PII rule, only its block, offsets, length and character class. Errors are logged as a type name or a fixed message, never the exception's text; a labelling failure's reason is a category plus field names from the schema, never what the model said. A failed labelling logs no residue text at all, since nothing then says which text is PII (see the leak found, below).
4. **The Run and the output document hold everything.** The Run is complete (the eval and `removal_precision` read it) and the output is the product; neither is sent anywhere by this phase.

**Two layers keep text out of a trace.** The first is the **allowlist**: every span is built by one pure payload function (`cvr.tracing.payload`) that emits only keys named in `ALLOWED_KEYS`, so a new field reaches a trace only if someone adds its name on purpose. The second is the **mask hook** the Langfuse client calls on every input, output and metadata value before it writes it: it drops any key off the allowlist (per mode), and redacts anything that is not a mapping, so a stray bare string never leaves. Around them: the client has its own tracer provider and never the global one, an export filter passes only spans from the SDK's scope that carry our marker, the LangChain callback handler and the `observe` decorator are banned by lint, and an error is recorded as its type name only. The mask cannot see a status message or an event, which is why the allowlist is the primary control and the status is a type name.

**Retention.** The Log Analytics workspace stays at 30 days, the minimum for its pricing tier (ticket 01). The ContainerApp tables, which hold the transform log, are set to 4 days (retention and total), the minimum Azure allows per table, by stage 12 of `scripts/provision-azure.sh`; the maintainer's read-back of the values is recorded on ticket 06. Langfuse Hobby keeps traces visible for 30 days, and in production they hold no text.

**The evidence is a canary test** (`tests/tracing/test_canary_leak.py`, in the default run, no model, no network). A copy of one Candidate is built at test time in which every content leaf, PII value and unplaceable fragment is a unique canary from a seeded generator (digit strings for phones, a unique domain for emails, words for text; dates stay real), checked for collisions with run ids and hashes, and rendered through all four Layouts. It goes through the API and through `reformat` with the real `RealLabeller` over a fake chat model, whose answers include a flawed one (a quote and a block id the model invented), a malformed one, a schema-invalid one, a refusal, a provider error and a defect, each carrying a canary. It asserts that no canary, nor its normalised forms (case folded, spaces removed, letters and digits only, and each word of it), appears in any exported span field; that no PII canary appears in the logs (standard output, standard error and every logger at DEBUG), the API's error bodies, the exceptions that escape the labeller with their chains, or the Run's failure reasons; and, as a second layer reading the parsed documents rather than the canary list, that no token of the source that is not the Layout's own text reaches a span. Positive controls stop it passing blind: the spans hold the run id and the counts, the logs hold content text, and a full-mode trace holds every kind of canary. Breaking the allowlist in a scratch run does not fail it by itself, because the mask hook catches what the payload function lets through; breaking both layers, or adding a text key to the allowlist, does.

**What the test found.** On a failed labelling the whole document is residue, and the log wrote every residue span's text. The backstops remove only emails, phones and URLs, so an address, a date of birth, a nationality, a referee's name all reached Log Analytics in full. Residue is now logged text-free whenever the labelling failed (`cvr.api.log`, with its own test).

**What the test cannot show.** A PII value that the labeller did not label and no backstop matches is unplaced text, so it goes to the review appendix by design (ADR-0004), and in a successful run its residue is logged in full. That is the labeller's recall on PII, which the eval measures (`removal_precision`, `pii_leak`), not a property a log filter can add. The canary test proves the boundary for what the system identified as PII.

**For real CVs this would change**, and each item is a decision for then, not now: Langfuse masking or self-hosted Langfuse in place of the allowlist alone; a data processing agreement with every processor (the provider, Langfuse, Azure); retention set by policy rather than by the minimum Azure allows; EU-bound processing for every provider, the Anthropic path included (Azure OpenAI on a Data Zone deployment is the Phase 2 comparison, ADR-0014); and logging no residue text at all, so that the labeller's misses cannot reach the logs either.

**Considered options:** Full text in every trace, with a Langfuse mask for PII (rejected: the mask hook sees values without their field names, and a regular expression finds emails and phones but not addresses or dates of birth). The mask hook alone (rejected: it does not cover status messages or events, and a missed key is silent). No text in the logs (rejected: the unplaced text is what a reviewer reads there, and the positive control that the logs still say something). Scrubbing the logs by pattern alone (rejected for PII a pattern cannot recognise; the removal's own record is the reliable list, so the logs strip by it).

**Consequence:** a change to what a span carries is a change to `ALLOWED_KEYS` and fails the canary test unless it is structure. Any new log field that carries text has to be PII-stripped through the same rule or the test finds it.
