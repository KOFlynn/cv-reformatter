# Provenance is checked per rendered unit; token multisets, PII and image checks cover its blind spots

The brief describes the added-text and dropped-text gates as multiset comparisons of tokens. A multiset is order-blind: swap two words inside a bullet, or move a word between bullets, and both gates still pass, so a bag of words does not prove the invariant. The primary check is therefore `provenance_violations`: every rendered unit (a bullet, a title, a skill, a date) must be an exact canonicalised substring of some source block, unless it is template text or a normalised date mapped back to its source. The multiset checks remain as the coarse backstop.

Provenance has its own blind spots, and each is closed by a separate hard gate rather than by stretching the definition:

- **A leaked email is correctly copied source text**, so neither `added_tokens` nor `provenance_violations` can see it. `pii_leak` is a separate gate that matches fixture PII values, with variants (digits-only phones, casefolded emails, whitespace-collapsed addresses), reporting each hit once under the most specific removal rule.
- **A photo is not text**, so no token metric can see it. `image_leak` compares the output document's embedded images by content hash against the template's own image set: any hash the template does not own is a leak, with its count. Membership rather than multiplicity, because a template image repeated in the output (a logo in every section header) is still the template's image, and a candidate's photo can never hash to one.
- **Template text is whitelisted by word**, so "Experience" is permitted wherever it appears. Provenance, which checks whole units against whole blocks, is what stops template words being used as filler.

All metrics share one `canonicalise()` and one `tokenise()`, held in `cvr.text` at the bottom of the dependency stack so eval, the golden-set generators and the pipeline all reach the same table without depending on each other. `canonicalise()` is NFC first, then an explicit confusable table (curly quotes, dashes, ellipsis, exotic spaces, invisible characters), then whitespace collapse. NFKC would do much of the table for free but also rewrites things that must stay (`½` → `1⁄2`, `™` → `TM`), so NFC plus an explicit table is deliberate. `tokenise()` canonicalises, splits on whitespace, strips punctuation from token edges only, and drops empties: `Engineer,` in the source matches `Engineer` in the output while `C++`, `O'Flynn` and `2019-2022` survive intact and typos stay protected. "Punctuation" here is the Unicode punctuation categories (P*), not symbols (S*): `+`, currency signs, `™` and `°` stay on a token edge, `#` and `%` do not. Both sides of every metric tokenise the same way, so the choice only has to be consistent, not perfect. No metric normalises on its own.

Canonicalising both sides creates one more blind spot: if the renderer silently straightens a curly apostrophe, no canonicalised metric notices, and the "punctuation is never changed" rule would be claimed but unchecked. `punctuation_fidelity` compares the raw located source span with the raw rendered unit, byte for byte, after provenance has found the span. It starts as a reported metric and is promoted to a hard gate once the baseline shows it is clean. The one deliberate modification the pipeline may make, stripping invisible characters, is a named rule (`NORM_INVISIBLE`) written to the transform log, because no token metric can ever see it.

**Consequence:** the "test the test" suite corrupts a fake pipeline one way at a time, and asserts each corruption fails exactly its declared blast radius. The rows "swap two words" (fails provenance, passes multisets), "re-emit the email" (fails PII, passes everything else) and "straighten an apostrophe" (fails punctuation fidelity, passes provenance) are the documented proof that no single check would have been enough.

**Amendment (Phase 1, ticket 05): a multi-span unit is checked through `split_map`, not the whole-unit substring rule.** A join produced by clipping a content claim around a removal (ADR-0008) is never itself a contiguous substring of its block — the clip leaves a gap — so `provenance_violations` takes a `split_map` of rendered unit to its ordered raw slices and, for a unit it names, requires every slice to be a canonicalised substring of one common block, each found strictly after the last. A join across two blocks, or the right slices in the wrong order, is a violation the whole-unit rule could never see, since the assembled string can still happen to read as something. The corruption row "join two slices out of source order" prints nothing different from row 0 — only the logged order is wrong — so it is the proof that only this check reads `split_map` at all. `punctuation_fidelity` correspondingly takes one raw pair per slice of a multi-span unit rather than one pair for the joined whole, which has no single source location to compare byte for byte.

**Amendment (Phase 1, ticket 05): the renderer round-trip test, not the eval gate, catches a composite line assembled in the wrong order.** `provenance_violations` and the multiset checks work in canonicalised tokens and whole units; swapping `entry.employer` and `entry.location`, or `start` and `end`, around the template's own comma or en dash produces a rendered unit that is still exactly the source text of some block (the pieces are real, just reattached to the wrong field), so no eval metric would fail. The renderer's own round-trip test (`render` a known `TransformedContent`, `adapt` the document back, compare field for field) is the one place this is caught, because the adapter recomposes each composite line by the same convention the template used to compose it and asserts against the field the text was meant to land in, not merely that the text exists somewhere. The adapter's own recomposition is itself an approximation for the same reason ADR-0008's text-box order is: the employer/location split is the first `", "` (no employer name in the golden set contains one of its own), and education's date line is told apart from a "details" paragraph of the same style by shape (the normaliser's three formatted forms, or the template's own en-dash join) rather than by any positional guarantee. Both limits are recorded here, not mitigated, because nothing in the golden set exercises the case that would need it.
