# 03: Verify through the claim ledger

**What to build:** The `verify` node and the types that bind labeller and verifier together. Input: the blocks from ticket 02 and a *labelling result*: either a reference-shaped content tree (every leaf a `{block_id, quote}` reference, `quote` mandatory, entries carrying one `dates` reference for the whole range block) plus a `removals` list of `{rule, block_id, quote}` with `rule` a closed enumeration of the eight text rules, or a *labelling failure*. Output: `VerifiedContent` (the tree in `CVContent` shape with `Span`s and multi-span units in place of strings), a flat list of `(path, Span)` claims, per-block residue. Matching is on canonicalised text through ticket 01's offset map; slices are raw; no case-folding. One claim ledger per block of `(start, end, claimant)`, filled in this order and no other: LLM removals in schema order → regex backstop (email, phone, URL) over every block → content in tree-walk order (name, profile, skills, education, experience, certifications, additional; list order within). A repeated quote takes the next unclaimed occurrence. Content overlapping a removal is clipped (one piece at an edge, two mid-range → a multi-span unit). Content overlapping content is a conflict: the later claimant is rejected, the range stays unclaimed. A quote that cannot be located rejects that one leaf. Coverage runs last over the finished ledger, over the flat claim list, never the tree, and emits residue runs; a run made only of `SEPARATORS` is separator residue (logged, not unplaced); anything else is unplaced text. A vocabulary-only `RM_HEADING` backstop (the four Layouts' headings, common synonyms, "Curriculum Vitae"; case-folded; trailing colon stripped) applies only to blocks holding no placed content. A labelling failure yields an empty tree, every block residue, and the run flagged. ADR-0008 is written in this ticket: removals before content, conflicts loud, residue versus unplaced text, the separator set and the ampersand, the vocabulary-only backstop and why (a false removal is silent, a false appendix entry is loud), text-box order as an approximation.

## Comments

### 2026-09-21: built, in review (branch `phase-1/03-verify-through-the-claim-ledger`)

**What was built.** In `cvr.models`: the labelling result, `Reference(block_id, quote)`, `ExperienceReference` and `EducationReference` (one `dates` reference each), `ContentReferences` mirroring `CVContent`, `RemovalLabel(rule, block_id, quote)` with `rule: TextRemovalRule` (a `Literal` of the eight text members of `RemovalRule`, so the JSON schema is a closed `enum` and a parsed value is the enum member), `Labelling(content, removals)`, `LabellingFailure(reason)`, `LabellingResult = Labelling | LabellingFailure`; and the verified side, `Unit(spans)` (one or more `Span`s of one block, ascending, non-overlapping, validated) with `VerifiedExperience`, `VerifiedEducation`, `VerifiedContent`, every leaf nullable and every list empty by default so `VerifiedContent()` is the labelling-failure tree. `tests/models/test_labelling.py` walks `Labelling.model_json_schema()`: every object's `required` equals its properties, `additionalProperties` is false, no property has a default, and the rule enum is exactly the eight. In `cvr.verify`: `verify(blocks, labelling) -> Verified(content, claims, removals, rejections, residue, ledgers, label_failed)` with `Verified.unplaced` (the non-separator residue Spans); `Claim(path, span)`, `Rejection(path, block_id, quote, reason)`, `Residue(span, separator)`; `verify.ledger` (`Ledger`, `LedgerEntry(start, end, claimant, kind)`) and `verify.backstops` (`pii_matches`, `heading_key`, `HEADING_VOCABULARY`). Tests in `tests/verify/` cover every checkbox by name. ADR-0008 written; `CONTEXT.md` Claim and Backstop amended; `CLAUDE.md` records the package. 1592 tests pass in about 33 seconds; ruff clean.

**Decisions beyond the ticket text.**

- The labelling-result and verified types live in `cvr.models`, not in a `label` module: the spec's dependency direction has `verify` on `text` and `models` only and `transform` on `models` and `text`, and both consume these types, so `models` is the one place both can reach. `Unit` is one type for both the one-piece and the multi-span case (a multi-span unit is a `Unit` with more than one span) so transform never branches on a union.
- Paths are `name`, `profile[0]`, `experience[1].bullets[2]`, `education[0].dates`, and `removals[3]` for an LLM removal. A multi-span unit is several `Claim`s under one path; `Claim` is per piece so coverage can sum over the flat list.
- **Conflict semantics.** The spec's "the later claimant is rejected and the range stays unclaimed" is read as: the later claimant gets no claim, the earlier keeps what it holds, and whatever of the loser's range the winner does not hold is residue. The alternative (revoke both) was rejected because c06's third identical quote would then pull two real placements into the appendix. **For the maintainer:** the oracle variant table in `.scratch/phase-1/spec.md` ("claims one range twice under two fields → the range is unplaced") reads as revoke-both; under this implementation an exact duplicate leaves the range placed once and logs the rejection, and only a partial overlap surfaces text. Ticket 06 should write that variant with a partial overlap or amend the table.
- Rejection reasons are `unlocatable` (no such block, empty quote, or no occurrence on canonical text), `conflict` (occurrences exist but every one overlaps placed content; c06's third quote is this) and `removed` (the first content-free occurrence lies wholly inside removals, so clipping leaves nothing). A content claim takes the *first* occurrence free of content and does not look further if that occurrence is wholly removed.
- Clipped pieces are trimmed of edge whitespace (`str.isspace` only, never other separators) and a piece that trims to nothing is dropped; the trimmed whitespace is unclaimed and comes out as separator residue. So c08's bullet is a prefix without its trailing space, and transform's single-space join makes sense for a mid-range clip. Removals are not trimmed.
- Residue runs are raw and untrimmed (`" & "`, `" delta"`); the appendix renderer may strip. `is_separator_residue` decides `separator` on the raw run.
- An LLM removal whose occurrence is already wholly inside an earlier removal records nothing and rejects nothing: it is reported once, under the earlier rule (RM_REFEREE before the backstop's RM_EMAIL, as the glossary's Removal entry says). A removal that partly overlaps an earlier one records the remainder. The regex backstop's own three patterns run email, phone, URL, and a span matched by an earlier pattern is not offered to a later one (`pii_matches`).
- The heading backstop runs **after** content and **before** coverage, as a fifth stage, because "only blocks holding no placed content" can only be known once content is placed. The fill-order test records the five stage functions being called in sequence by monkeypatching the module attributes `verify` looks up at call time, in addition to the behavioural test (a content claim over an email is clipped with no removal labelled).
- The heading vocabulary holds all headings the four Layouts print, including `Contact`, `References` and `Referees` (the prompt says the source's own headings go under RM_HEADING), document titles (`Curriculum Vitae`, `CV`, `Resume`, `Résumé`), and common synonyms grouped by template section. `heading_key` casefolds, collapses whitespace, reads `&` as `and` and strips trailing colons and spaces; the match is whole-block. Sub-heading words (`Languages`, `Interests`, `Publications`, `Volunteering`) are deliberately absent, pinned by a test.
- The phone pattern is digit groups joined by single spaces, dots or dashes, optionally bracketed, optionally `+`-prefixed, nine to fifteen digits in all, so `2019-2022` (eight digits) and `2020-01 - 2021-06` (a spaced dash breaks the run) are never phones; every golden-set shape and seven date shapes are pinned. The URL pattern needs `http(s)://` or `www.` and gives back trailing sentence punctuation and a closing bracket. The email pattern is the usual local@domain.tld.
- On a `LabellingFailure` the backstops still run (regex over every block; the heading vocabulary over every block, since none holds content), so a PII value cannot reach the appendix through a bad day for the LLM (ADR-0004: removal takes precedence over the appendix). A test pins it. "Every block is residue" therefore means every block's unremoved text is residue.
- `Verified` is a frozen dataclass in `cvr.verify` as `ParsedDocument` is in `cvr.parse`: a node's return value, never loaded from JSON. `Verified.ledgers` is `dict[block_id, list[LedgerEntry]]` sorted by position, for the `Run` record of ticket 04.
- Matching finds occurrences with `str.find` stepping one character, so overlapping occurrences are candidates; the ledger's content check makes the second of an overlapping pair a conflict, never a double placement.
- Exploratory (not committed): a crude oracle over c03, c06 and c08 in all four Layouts placed every leaf it could locate, removed every phone (including the text-box Layout's no-break-space one), email, URL and every Layout heading, and never took a date for a phone. The conflicts it produced were its own (it takes the first block containing "Limerick", which is the address line), which is exactly the per-entry location work ticket 06's oracle does.
