# 17: The Azure provider in RealLabeller

**What to build:** `RealLabeller` can label through Azure OpenAI, selected by configuration (`CVR_LABEL_*`) with no code change. The `azure_openai` provider's arguments (deployment, endpoint, API version, a token provider built from the default Azure credential with the scope found in ticket 01) are isolated, as the Anthropic ones are, and no key path exists. The price table gains gpt-5.4 at Data Zone prices, checked on the day. An offline test checks the `Labelling` and `Additions` schemas against Azure's strict-mode limits.

**Blocked by:** 01, 12

**Status:** done

- [x] `langchain-openai` and `azure-identity` added; the lock file updated
- [x] Over fakes: an Azure config yields the expected chat-model arguments, a token provider and never a key; a config with a key is refused as misconfigured (tested)
- [x] Every configured model has a price, and the test fails loudly for one that does not; cached-input pricing is included if caching is used
- [x] The schema check covers: every field required, no additional properties, nesting depth, unsupported keywords, root not `anyOf`. If either schema fails it, the fix bumps the schema version and an eval on the deployed provider is shown
- [x] The image check is run and pasted (by the deploy job after PR #41 merged, see the 2026-10-24 post-merge comment); the runtime-import test still holds (it does: `tests/docker/` green)

## Comments

- 2026-10-24: Built on `phase-2/t17` (off `phase-2/release-11-17`).
  - **Dependencies.** `uv add langchain-openai azure-identity` (langchain-openai 1.7.2, openai 3.37.0, azure-identity 1.26.0, with msal, cryptography, tiktoken and azure-core). Installed they weigh about 40 MB unpacked, so the 350 MB image should land near 385-390 MB; `scripts/check-image.sh` has no size ceiling. It was **not** run here: its last step makes a real `/reformat` call to Anthropic, which this ticket's build ran without. The maintainer runs it (`sh scripts/check-image.sh`) and pastes the size; that box stays open for that reason. The runtime-import test (`tests/docker/`) holds.
  - **Provider.** `src/cvr/label/azure_openai.py` (new, so `labeller.py` changes stay small): `azure_kwargs` builds `AzureChatOpenAI` arguments through `init_chat_model(model_provider="azure_openai")`: `azure_endpoint`, `azure_deployment` (default: the model name), `api_version` (default `2025-04-01-preview`), `azure_ad_token_provider=get_bearer_token_provider(DefaultAzureCredential(), "https://ai.azure.com/.default")` (the scope ticket 01 found; `CVR_LABEL_AZURE_SCOPE` overrides it for the documented cognitiveservices fallback), `reasoning_effort`, `max_completion_tokens` 128000 (chat-completions reasoning models reject `max_tokens`; langchain-openai's field alias is `max_completion_tokens`), `max_retries` 2, temperature only when set. `azure_error` classifies `openai` and `azure.core` exceptions like `anthropic_error`. Env vars: `CVR_LABEL_PROVIDER=azure_openai`, `CVR_LABEL_MODEL=gpt-5.4`, `CVR_LABEL_AZURE_ENDPOINT` (required), `_DEPLOYMENT`, `_API_VERSION`, `_SCOPE`.
  - **No key path.** `AzureChatOpenAI` silently reads `AZURE_OPENAI_API_KEY`, `OPENAI_API_KEY` and `AZURE_OPENAI_AD_TOKEN` from the environment, so `api_key=None` and `azure_ad_token=None` are passed explicitly (a test sets all three and checks the built model holds neither). A key or token argument in `CVR_LABEL_EXTRA` is refused as `LabellerMisconfigured`, and the message does not echo the value.
  - **Decisions beyond the ticket.** (1) Azure settings are `LabellerConfig` fields that appear in `as_dict()` only when set, so the Anthropic cache keys and reports are unchanged; the endpoint is left out of `as_dict()` because that dict reaches reports and traces. (2) `max` effort is refused for Azure: the reasoning guide lists `max` for GPT-6 and GPT-5.6 on the Responses API only; gpt-5.4 takes `none|low|medium|high|xhigh` and the labeller offers no `none`. (3) Strict mode is `with_structured_output(..., method="json_schema", strict=True)`, passed for Azure only (the Anthropic binding is untouched). (4) A refusal is also recognised from OpenAI's message `refusal` field, so it becomes a labelling failure, not a "schema mismatch". (5) The API version default is a dated preview rather than `v1`: the v1 API is reached with the plain `OpenAI` client and a `/openai/v1/` base URL, not `AzureChatOpenAI`'s deployment paths. Whether to move to `ChatOpenAI` on `/openai/v1/` is for the live proof (ticket 18/19) to settle. (6) `KNOWN_MODELS` in `config.py` plus `require_price` make "every configured model has a price" a failing test; `estimate_cost` still returns 0 for an unknown model so accounting never crashes.
  - **Prices.** gpt-5.4, Data Zone Standard, up to 272K context: $2.75 input, $16.50 output per million tokens (cached input $0.275, not in the table because nothing requests caching; Azure's automatic caching would only lower the real cost). Source: Microsoft's Azure Retail Prices API (`https://prices.azure.com/api/retail/prices`, meters `5.4 inp Dz`, `5.4 opt Dz`, `5.4 cd inp Dz`, `northeurope`, effective 2026-06-01, the same in every EU Data Zone region), read 2026-10-24. The human pricing page `https://azure.microsoft.com/en-us/pricing/details/azure-openai/` renders its GPT-5.4 rows as `$-` when fetched without a browser, so it could not be read directly; a third-party aggregator agreed. Uncertainty: the page itself was not seen, and the API reports `retailPrice` (list, pay-as-you-go), which is what the estimate wants.
  - **Schema check** (`tests/label/test_azure_strict_schema.py`, limits from `https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/structured-outputs`, page dated 2026-08-24: 100 object properties, five levels of nesting, all fields required, `additionalProperties: false`, root not `anyOf`, the unsupported-keyword table). Both schemas pass: `Labelling` 49 properties, object nesting 4; `Additions` 5 properties, nesting 3; no unsupported keyword, enum of 8 values (the page states no enum limit), nullable fields are `anyOf` with `null`. One ambiguity to flag, not a failure: the page does not say whether "levels of nesting" counts arrays as well as objects. Counting arrays too, `Labelling` is 6 (one over) and `Additions` 4. I applied the object reading (the one OpenAI's examples fit) and recorded both figures in the test. If the first live call on the deployment rejects `Labelling`, the fix is a schema change (a version bump and an eval on the deployed provider); no schema was changed here.
  - **Not done.** No real call to Azure or Anthropic was made. The Azure spike test (`tests/label/test_azure_spike.py`) is skipped without `CVR_LABEL_PROVIDER=azure_openai` and `CVR_LABEL_AZURE_ENDPOINT`. The existing `tests/label/test_spike.py` reads `run.config.model`, but `LabelRun.config` is a dict; it is skipped without a key so nobody has noticed. Left alone.


**2026-10-24, review fixes (S3, S4).** `openai.LengthFinishReasonError` (the answer hit the token limit) is now a `LabellingFailure` with the reason `invalid JSON`, the category Anthropic's `max_tokens` truncation gets, and `openai.ContentFilterFinishReasonError` is one with `the model refused to answer`, as a refusal is (`azure_failure_reason`, called from `failure_reason`); both fell through to `LabellerMisconfigured` and a 500 before. The credential is `DefaultAzureCredential(exclude_environment_credential=True)`, so a client secret in the environment is not a credential path: the chain is the managed identity in Container Apps and the developer's sign-in locally. The deployed app uses a system-assigned managed identity (ticket 18 provisions it); the scope and API version are confirmed by ticket 19's live proof. `CVR_LABEL_EXTRA` may not carry `base_url`, `openai_api_base`, `azure_endpoint` or `default_headers` (the bearer token could be redirected). Correction to "Not done" above: `tests/label/test_spike.py` read `run.config.model` on a dict; fixed in the review (it is skipped without a key).
